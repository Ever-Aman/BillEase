# Signed revoked-work recovery

`POST /v1/recovery/upload` is an upload-only endpoint for previously enrolled devices with retained business membership. It verifies an Ed25519 signature, binds the original actor to the device and retains the original operation ID, payload, claimed role, dependencies and signature. Claimed timestamps never grant permission. An optional signed `originalRole` must match the retained membership role; mismatches remain quarantined for manual reconciliation. Legacy clients without this field use the retained server membership role. Membership roles are immutable through setup APIs.

Every mutation requires a separate current, active business owner decision. Customer creation/update, bills, deliveries, staff requests, repayments and returns use their existing command handlers. Signed dependency operation IDs must already be committed before dependent work can be accepted; owners reconcile customer, bill and delivery in that order. A failed acceptance leaves the quarantine original pending, with no partial financial changes.

Uncertain owner actions carry `{operationType,method,path,payload}`. The payload is the unchanged original request; the operation ID is never replaced. Supported typed commands are `return.record`, `repayment.cash`, `balance.opening`, `advance.apply`, `bill.cancel`, `payment.correct`, `delivery.correct`, `ledger.correct`, `payment.verify`, `credit.review`, `delivery.review`, `request.decide` and `quotation.create`. Each command has a strict schema and exact route/target check; the recovery service never replays an arbitrary route. Existing accepted operations must match actor, type and original payload hash and return their original outcome without another mutation. The owner decision and financial mutation commit in one transaction.

Unsupported actions, including document settings and catalogue management, initially remain pending with an explicit `retained` result and an audited review note. For the allowlisted nonfinancial settings/catalogue paths, a current owner can close review using `POST /businesses/:businessId/quarantine/:deviceId/:operationId/reconcile` with `{resolution:"already_applied"|"discarded",note,decisionOperationId}`. This records `decision:"reconciled"` and `status:"manually_reconciled"`, preserves the original, and audits the resolution without executing any command. This endpoint rejects typed financial actions. The owner list includes `manual_reconciliation_available` and `original_actor_email`. Originals without an idempotent operation ID are not converted into new financial commands. Recovery upload acknowledgement means quarantine storage, not acceptance or invoice issuance. Device authorization history records server-observed role grants on enrollment/refresh; this history does not prove when offline work was created. Owner review remains required.

Verification covers real HTTP upload/read separation after device or membership revocation, signed provenance, unchanged originals, customer/bill/delivery dependencies, original-owner returns, typed prior-commit reconciliation, role mismatch rejection and unsupported-action retention. The Flutter helper test verifies typed mapping without modifying original request objects.
